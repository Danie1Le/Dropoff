# Spring Modulith's event publication registry is the outbox

An event must reach Kafka once the change that caused it commits, and never for a change that rolled back, so the project needs a transactional outbox. From M2, module listeners will use `@ApplicationModuleListener`, which writes every event to Spring Modulith's `event_publication` table in the same transaction as the change and retries incomplete ones. At M5, `spring-modulith-events-kafka` relays events annotated `@Externalized("<topic>::#{orderId()}")` to Kafka from that same table, and completed publications are deleted. Delivery is at least once, so consumers dedupe by the event's `eventId` in `processed_events`. A hand-written `outbox` table with its own relay job was rejected: it duplicates what the registry already does and adds code to get wrong. `order_events` stays a separate, permanent audit history written in the same transaction; neither table feeds the other. `CourierLocationUpdated` bypasses the outbox (a plain `@EventListener` before the split, `KafkaTemplate` after it), because a lost update is replaced within 5 s.
