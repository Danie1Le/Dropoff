# Service split: a database per service and a local menu copy in order-service

At M5 the monolith splits into merchant-, order- and dispatch-service. One Postgres container hosts one database per service (`merchant_db`, `order_db`, `dispatch_db`), each with its own user, so no service can join or write another's tables, and the cross-service foreign keys from ADR-0003 are dropped. To validate and price an order, order-service reads a local `menu_item_copies` table that merchant-service keeps in sync with `MenuItemChanged` and `MerchantChanged` events on a compacted Kafka topic keyed by `menuItemId`; on an empty start, order-service rebuilds the copy by reading that topic from the beginning. Unknown item ids are rejected with 422, which replaces the foreign key. A synchronous REST call to merchant-service for every order was rejected: with it, nobody could order while merchant-service was down. The price of the copy is that a just-changed price can be a few milliseconds stale, which the price snapshot then records. `OrderReady` carries the merchant's lat/lng, so dispatch needs no merchant data.
