# M7 — Performance: build guide

Goal: measured load and one or two measured wins. First a k6 harness that can load the three services the same way
every time, then a baseline from it, then one or two optimizations chosen from the baseline's numbers, and finally a
write-up with the before and after tables.

`docs/PLAN.md` (section "M7 — Performance") is the spec, and ticket #35 holds the method. This file adds the build
order, the issue for each PR, and implementation notes for each PR. If the two disagree, `PLAN.md` wins.

**Starts after:** M6 is merged. The load runs against the service images and the `demo` profile from M6-3, and the
dispatch p95 comes from the M6-1 metrics on the M6-2 Grafana dashboard.

## Every PR

1. Branch `feat/m7-N-<slug>` from `main`.
2. Write the tests from the issue's "Done when" list first. M7-2 and M7-5 have no tests (a measurement PR and a docs
   PR); M7-3/4 keep every existing test green and take their numbers from the same harness.
3. Run `./gradlew build` (Spotless, Error Prone, NullAway, tests). Docker must be running for the ITs.
4. Tick the M7 items in `docs/roadmap.html`, and bump its "Data last synced" date.
5. Open the PR with `Closes #<issue>`.

## Implementation notes

### M7-1 Load test harness
- **SQL:** `generate_series` builds 200,000 rows in one `INSERT … SELECT`, with every value computed from the row
  number, so each reseed is identical and runs compare fairly. A temp table numbered with `row_number() OVER
  (PARTITION BY …)` lets each order pick its merchant's menu items by number. `OVERRIDING SYSTEM VALUE` writes chosen
  ids into a `GENERATED ALWAYS` identity column. `UPDATE … FROM (SELECT … GROUP BY …)` sets every total from its lines
  in one statement. `ANALYZE` refreshes planner statistics after a bulk load. `pg_stat_statements` sums the calls and
  time of each normalized statement (`$1` in place of values) across every database.
- **Backend:** Open versus closed load models: k6's arrival-rate executors start requests on a schedule whatever the
  latency, so a slow server shows up as latency, not as a quietly lower request rate. Thresholds turn a run into pass
  or fail (p95 under 300 ms, errors under 1%). Tags split the numbers per endpoint and keep setup requests out of them.
  The load generator gets its own memory cap so it can't starve what it measures.

### M7-2 Baseline
- **SQL:** Reading `pg_stat_statements`: `total_exec_time` versus `mean_exec_time`, and why the top query by total
  time may be a cheap one called very often. `pg_stat_statements_reset()` before each run.
- **Backend:** p50, p95 and p99, and why the median of 3 runs. Recording the hardware and the commit SHA so the numbers
  can be reproduced.

### M7-3 and M7-4 Optimizations
- **SQL:** `EXPLAIN (ANALYZE, BUFFERS)`: actual rows against estimated rows, shared hits against reads, and the cost
  of a sort or an offset. Offset paging against keyset paging (`WHERE (created_at, id) < ($1, $2)`), and which index
  serves each.
- **Backend:** Changing one thing at a time and measuring with the same harness. Depending on the pick: a cache and its
  invalidation, batching to remove an N+1, or moving hot location writes to Redis.

### M7-5 Write-up
- **SQL:** None.
- **Backend:** Presenting results: a before and after table with the % change, and the EXPLAIN snippet that shows why.

Running the load tests (from M7-1; Docker must be running):

```bash
./gradlew :services:merchant:bootJar :services:order:bootJar :services:dispatch:bootJar :tools:simulator:installDist
docker compose --profile demo up -d --build      # the services and the simulator; wait for "Running 41 bots"
docker compose exec -T postgres psql -U order_user -d order_db -v ON_ERROR_STOP=1 -f - < ops/perf/seed-history.sql
docker compose --profile demo --profile load run --rm k6 run browse.js
docker compose --profile demo --profile load run --rm k6 run order-history.js
docker compose --profile demo --profile load run --rm k6 run place-orders.js
docker compose --profile demo --profile load down -v   # stop, and drop the data
```

The seed takes about 90 s and runs once per volume; a second run stops with "History already seeded". It adds 100
customers (ids 1000001 to 1000100) with 2,000 delivered or cancelled orders each, 200,000 in all, with about 400,000
order lines, so a customer's history is 100 pages of 20 and a deep page is a real offset.

| Script | `LOAD_PROFILE=short` (default) | `LOAD_PROFILE=full` (ticket #35) |
|---|---|---|
| `place-orders.js` | 2 to 10 orders/s over 1 min | 5 to 50 orders/s over 10 min |
| `browse.js` | 20 req/s for 1 min | 100 req/s for 5 min |
| `order-history.js` | 10 req/s for 1 min | 50 req/s for 5 min |

Runs stay short by default, since the machine is low on memory: a short run proves the harness and the stack work. Set
`LOAD_PROFILE=full` for the M7-2 baseline and the M7-3/4 comparisons, for example
`LOAD_PROFILE=full docker compose --profile demo --profile load run --rm k6 run place-orders.js`. Every script fails
the run (exit code 99) if p95 reaches 300 ms or errors reach 1%. The summary shows p50 (`med`), p95 and p99 for each
endpoint. Add `--summary-export=/results/<name>.json` after `run` to keep it as JSON in `ops/k6/results/`
(git-ignored).

k6 is capped at 256 MB. A short run used about 15 MB, so even 100 VUs at full load fit. `place-orders` sends its
orders to the simulator's merchants, so the merchant and courier bots accept and deliver them, and the dispatch p95 on
the Grafana dashboard moves with the load. The 30 seeded couriers deliver far fewer than 10 orders/s: in a short run
all 30 went BUSY and most orders waited READY for a courier. That limit is the simulator's, not dispatch's, so M7-2
reads dispatch p95 with it in mind.

`pg_stat_statements` is on in the Compose Postgres (`02-pg-stat-statements.sql`; on an older volume run
`docker compose down -v` once to get it). Reset it before a run and read the top 5 after, as the superuser in the
`dropoff` database:

```bash
docker compose exec postgres psql -U dropoff -d dropoff -c "SELECT pg_stat_statements_reset()"
docker compose exec postgres psql -U dropoff -d dropoff -c "SELECT d.datname, s.calls,
  round(s.total_exec_time) AS total_ms, round(s.mean_exec_time::numeric, 2) AS mean_ms, left(s.query, 80) AS query
  FROM pg_stat_statements s JOIN pg_database d ON d.oid = s.dbid ORDER BY s.total_exec_time DESC LIMIT 5"
```
